**Pipit**은 디스코드를 중심으로 모여 함께 작업하는 작은 개발팀을 위한 디스코드 봇입니다. 팀이 이미 대화하는 자리에 팀의 워크플로우를 접어 넣습니다 — 봇 하나, 대시보드 하나로 전부 설정합니다.

- **PR·이슈 리마인더** — GitHub App이 등록·업데이트·리뷰·머지·닫힘을 지정한 채널로 알리고, 필요한 사람만 멘션하며, 담당자·리뷰어가 바뀌면 원래 알림 메시지를 최신 상태로 고칩니다
- **리액션 롤** — 봇이 패널 메시지를 발행하고, 멤버가 반응하면 역할을 부여합니다
- **초대 로거** — 입장·퇴장 메시지, 초대 코드별 유입 수, 기록 채널, 입장 시 자동 역할
- **감사 로그** — 대시보드·디스코드에서 누가 무엇을 했는지, GitHub 발송과 멤버 입장·퇴장. 90일 보관
- **음악** — 음성 채널에서 함께 듣는 재생. 교체 가능한 music worker가 뒤에서 처리합니다
- **대시보드** — 위 설정 전부를 라이트/다크 테마로, 자체 로그인 화면 뒤에서: 비밀번호 계정, 사용 중인 OIDC 제공자, Discord 또는 GitHub

Sapphire와 discord.js로 만들었습니다. 음악 소스는 **교체 가능**합니다: pipit-bot은 별도의 music worker에 요청하고, 공유 볼륨에 준비된 파일을 스트리밍합니다. [docs/music-backend.md](./docs/music-backend.md)를 참고하세요.

## 스택

- Node.js 18+, TypeScript, Sapphire
- discord.js v14, discord-player v7
- 내장 **pipit-api** (잡 레지스트리, 내부 콜백, 대시보드 API)
- PostgreSQL 16(drizzle) — 봇이 계속 쌓는 데이터. 설정은 JSON 파일로 남습니다
- Yarn 4, Docker Compose

## 환경 변수

`.env.example`을 `.env`로 복사합니다 (`yarn start:dev`용으로 `.env.development.local`도 선택적으로).

```ini
BOT_TOKEN=
STREAM_ROOT=/streams
API_PORT=3000
INTERNAL_TOKEN=
GITHUB_WEBHOOK_SECRET=
GITHUB_APP_ID=
GITHUB_APP_PRIVATE_KEY=
GITHUB_APP_PRIVATE_KEY_PATH=
GITHUB_APP_INSTALLATION_ID=
MUSIC_WORKER_URL=http://music-worker:8080
# PostgreSQL (필수). 워크스페이스 compose는 자기 postgres 서비스로 설정합니다
DATABASE_HOST=
DATABASE_PORT=5432
DATABASE_USERNAME=
DATABASE_PASSWORD=
DATABASE_NAME=
# 또는 URL 하나로(설정돼 있으면 이쪽을 씁니다)
DATABASE_URL=
PIPIT_API_URL=http://127.0.0.1:3000
# 대시보드를 여는 주소: 로그인 콜백과 음악 채널 리모컨의 링크
DASHBOARD_URL=
# 세션 쿠키 서명. 프로덕션에서 필수
DASHBOARD_SESSION_SECRET=
DASHBOARD_ADMIN_GROUPS=pipit-admins
# 첫 관리자. 비밀번호 계정이 하나도 없을 때 한 번 만듭니다
DASHBOARD_BOOTSTRAP_USERNAME=
DASHBOARD_BOOTSTRAP_PASSWORD=
OIDC_ISSUER=
OIDC_CLIENT_ID=
OIDC_CLIENT_SECRET=
# 기본값: openid profile email groups
OIDC_SCOPES=
# 로그인 화면의 버튼 이름. 기본값: SSO
OIDC_DISPLAY_NAME=
# Discord·GitHub 로그인(봇 토큰·GitHub App과 별개인 OAuth 앱)
DISCORD_OAUTH_CLIENT_ID=
DISCORD_OAUTH_CLIENT_SECRET=
GITHUB_OAUTH_CLIENT_ID=
GITHUB_OAUTH_CLIENT_SECRET=
```

`/internal/*`은 공개 호스트에 노출하지 않습니다. music worker 콜백은 `INTERNAL_TOKEN`을 씁니다.

### 대시보드 로그인

로그인은 대시보드의 **로그인 화면**(`/login`)에서 시작하고, 끝나면 원래 가려던 페이지로 돌아갑니다. 화면에는 켜진 방법만 나옵니다:

- **비밀번호** — 관리자가 대시보드에서 만든 계정입니다. 공개 가입은 없습니다. 비밀번호는 8자 이상이고 대문자·소문자·숫자·기호 중 두 종류 이상을 섞어야 합니다. 첫 관리자는 `DASHBOARD_BOOTSTRAP_USERNAME` / `DASHBOARD_BOOTSTRAP_PASSWORD`로 만듭니다: 비밀번호 계정이 하나도 없을 때 한 번 만들고, 그 뒤로는 덮어쓰지 않습니다 — 비밀번호는 대시보드에서 바꾸세요
- **OIDC**(Authorization Code + PKCE) — Authentik과 Dex는 동작이 확인됐고, 이 플로우를 지원하는 다른 제공자도 쓸 수 있습니다. `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`을 설정하고 redirect URI로 **`<DASHBOARD_URL>/api/auth/callback/oidc`** 를 등록하세요. `OIDC_DISPLAY_NAME`이 버튼 이름입니다(기본 `SSO`)
- **Discord** — Discord Developer Portal의 OAuth2 앱(`DISCORD_OAUTH_CLIENT_ID`/`_SECRET`, redirect `<DASHBOARD_URL>/api/auth/callback/discord`, 스코프 `identify`). 봇이 있는 서버의 멤버만 들어오고, 처음 온 사람은 관리자가 아닌 사용자가 됩니다
- **GitHub** — GitHub OAuth 앱(`GITHUB_OAUTH_CLIENT_ID`/`_SECRET`, callback `<DASHBOARD_URL>/api/auth/callback/github`). 사용자에 이미 등록된 GitHub 로그인만 들어옵니다 — 사용자 페이지에서 먼저 넣으세요

로그인은 봇이 직접 처리합니다([Better Auth](https://www.better-auth.com)). 이 compose에 인증 프록시 컨테이너는 없습니다. 세션은 7일이며 데이터베이스에 둡니다. 로그인 시도는 주소별로 횟수를 제한합니다. 로그인·실패한 시도·로그아웃은 감사 로그에 남고, 비밀번호는 절대 남기지 않습니다.

**어떤 방법을 켤지**는 `data/auth-settings.json`(`{"password": true, "oidc": true}`)이며, 설정 페이지에서 바꿉니다. 필요한 환경 변수가 없는 방법은 켤 수 없고, 마지막으로 켜진 방법은 끌 수 없습니다. 잠겼다면 편집기로 파일을 고치고 다시 시작하세요: 손상됐거나 전부 끈 파일은 무시하고, 설정된 방법을 모두 켠 채 시작하며 로그에 남깁니다. 비밀은 언제나 환경 변수에만 둡니다.

**쓰기 권한**은 그룹으로 정합니다: `DASHBOARD_ADMIN_GROUPS`를 사람의 그룹과 대소문자 구분 없이 전체 일치로 비교합니다 — OIDC 제공자가 `groups` 클레임으로 내려주는 그룹과, 대시보드에서 준 그룹 둘 다입니다. 일부 제공자는 `groups` 스코프를 요청해야만 그 클레임을 내려주므로(Dex가 그렇습니다) 기본 `OIDC_SCOPES`에 포함돼 있습니다. 값은 공백 또는 쉼표로 구분하며 `openid`를 반드시 포함해야 합니다. 그룹 이름은 제공자가 부르는 그대로 적으세요 — 예를 들어 Dex의 GitHub 커넥터는 그룹을 `org:team`(`teamNameField: slug`이면 `org:team-slug`)으로 부르므로 `DASHBOARD_ADMIN_GROUPS=my-org:admins`처럼 씁니다. 첫 관리자와 개발용 `admin`은 목록의 첫 그룹에 들어갑니다.

로그인은 제공자의 이메일이 아니라 식별자로 사람에게 이어집니다: Discord는 디스코드 ID로, GitHub와 OIDC 사용자 이름은 GitHub 로그인(GitHub 페이지의 계정 연결)으로. 그래서 어느 방법으로 들어와도 같은 사람입니다 — 디스코드 계정·개인 재생목록·결산도 그대로. 아무와도 이어지지 않는 OIDC 로그인은 새 사용자가 됩니다. 저절로 이어지지 않으면 관리자가 **사용자 페이지**(`/users`)에서 GitHub 로그인이나 디스코드 계정을 넣습니다. 이 페이지에서 비밀번호 계정 추가, 비밀번호 설정(그 사람의 세션은 모두 끊김), 관리자 권한 주기·빼기, 사용자 삭제도 합니다. ID 제공자가 준 관리자 권한은 제공자에서 바꾸고, 관리자는 삭제할 수 없습니다 — 먼저 권한을 빼세요. 제공자에 연결할 수 없으면 그 방법의 로그인은 `502`와 `{"error":"The identity provider could not be reached."}`로 응답하고 봇이 원인을 로그에 남깁니다. 다음 시도에서 다시 연결합니다.

`DASHBOARD_URL`은 대시보드를 여는 주소입니다: 로그인 콜백 주소를 이것으로 만들고, 음악 채널 리모컨이 그 음악 페이지로 연결합니다. `http`·`https` 주소만 받으며, 그 밖의 값이면 봇이 시작하지 않습니다. 없으면 로그인은 요청마다 주소를 읽고, 리모컨에는 링크가 없습니다.

`NODE_ENV=development`에서는 고정 계정 둘, `admin` / `admin1234!`(admin)과 `member` / `member1234!`를 만듭니다. 프로덕션에서는 절대 만들지 않고, 데이터베이스에 그런 계정이 있으면 시작하지 않습니다. 프로덕션에서는 `DASHBOARD_SESSION_SECRET`이 필수입니다.

### 언어

Pipit은 영어와 한국어를 씁니다. 언어는 세 가지로 정해집니다:

- **채널에 올라가는 메시지** — 음악 채널 배너, GitHub 알림, 입장·퇴장 기록, 리액션 롤 안내, 결산 — 는 서버의 **메시지 언어**(기본 영어)를 따르고, 기능마다 그 페이지에서 따로 고를 수 있습니다(페이지 머리의 "메시지 언어", 결산은 결산 설정 카드)
- **한 사람에게만 보이는 응답** — 슬래시 명령 응답, 음악 리모컨의 입력 창과 검색 결과 — 은 그 사람의 **디스코드 언어**를 따릅니다. 슬래시 명령 설명도 두 언어로 등록되어 디스코드가 각자의 언어로 보여 줍니다
- **대시보드** 는 개인이 고른 언어(머리의 언어 메뉴), 그다음 서버의 대시보드 기본 언어, 그다음 브라우저 언어를 따릅니다. 로그인 화면은 브라우저 언어

서버 기본값과 기능별 언어는 설정 페이지의 **언어** 카드와 `data/language.json`에 있습니다. 운영자가 쓴 문구 — GitHub 템플릿, 입장 메시지, 리액션 롤 패널 — 는 쓴 그대로 보내고, 기본 문구만 언어를 따릅니다(봇이 채우는 `{event}`도). 음악 채널 배너는 v0.8.3 전까지 항상 한국어였습니다: **계속 한국어로 쓰려면 메시지 언어(또는 음악 언어)를 한국어로 바꾸세요.**

### 데이터: 데이터베이스와 `data/`

봇이 **만들어 내고 계속 쌓는 것**은 **PostgreSQL**(필수)에 둡니다: 추적 중인 GitHub 메시지, 음악 채널 배너 메시지, 초대 통계, 감사 로그, 재생목록, 리액션 롤 패널, 대시보드 사용자와 세션(GitHub ↔ 디스코드 계정 연결 포함), 음악 재생 기록. **사람이 열어 고치는 설정**은 `data/` 아래 JSON 파일로 남습니다(`runtime-config.json`, `guild-events.json`, `github-notify.json`, `playback-options.json`, `features.json`, `audit-settings.json`, `music-recap.json`, `auth-settings.json`, `language.json`; gitignore 대상) — 대시보드에 들어갈 수 없을 때도 편집기로 고칠 수 있게. Docker에서는 `./pipit-bot/data:/app/data`를 마운트하세요.

- **시작** — 봇은 데이터베이스를 최대 2분까지 기다리고(아직 뜨는 중인 컨테이너도 괜찮습니다) 마이그레이션을 적용합니다. 붙을 데이터베이스가 없으면 시작하지 않습니다
- **데이터베이스가 없던 릴리즈에서 올릴 때** — 첫 시작에서 이제 데이터베이스에 두는 파일을 한 번 옮기고, 파일 이름을 `*.migrated`로 바꿉니다(지우지 않습니다). 무엇을 옮겼는지 로그에 남습니다
- **이전 이미지로 되돌릴 때** — 봇을 멈추고 `data/`의 `*.migrated` 파일 이름을 되돌린(꼬리를 뗀) 뒤 이전 이미지를 시작합니다. 올린 뒤 데이터베이스에 쌓인 것은 따라가지 않습니다 — 그리고 다시 올릴 때 이전 이미지에서 바꾼 것도 따라오지 않습니다: 다시 나타난 파일은 시각 붙은 이름으로 치워 두고(로그에 남습니다), `github-notify.json`에 되살아난 계정 연결은 다시 뺍니다. 그런 변경은 대시보드에서 다시 넣으세요
- **백업**은 이제 두 곳입니다: 데이터베이스와 `data/`

워크스페이스 루트의 compose 파일은 봇 옆에 `postgres:16-alpine` 서비스를 띄웁니다. 따로 쓰는 PostgreSQL이 있으면 봇을 그쪽으로 두세요.

봇은 `DATABASE_HOST`, `DATABASE_PORT`(기본 5432), `DATABASE_USERNAME`, `DATABASE_PASSWORD`, `DATABASE_NAME`으로 PostgreSQL에 붙습니다 — 이렇게 하면 비밀번호를 인코딩할 필요가 없습니다. `DATABASE_URL`도 쓸 수 있고, 설정돼 있으면 그쪽을 씁니다(URL만 주는 관리형 DB나 `sslmode` 같은 옵션). 둘 다 있으면 로그에 그렇다고 남깁니다. 로그에는 붙은 호스트와 데이터베이스만 남고 비밀번호는 남지 않습니다.

## GitHub 알림

PR·이슈 활동은 **GitHub App**이 전달합니다. App 하나를 등록해 원하는 저장소에 설치하면, 설치된 모든 저장소가 같은 엔드포인트로 보고합니다.

| App 설정       | 값                                                                                    |
| -------------- | ------------------------------------------------------------------------------------- |
| Webhook URL    | `https://<public-host>/webhooks/github`                                               |
| Webhook secret | `GITHUB_WEBHOOK_SECRET`과 같은 값                                                     |
| 저장소 권한    | `Metadata: Read-only`, `Pull requests: Read-only`, `Issues: Read-only`                |
| 조직 권한      | `Members: Read-only` (선택 — 계정 매핑 피커에만 필요)                                 |
| 구독 이벤트    | Pull request, Pull request review, Pull request review comment, Issues, Issue comment |

인터넷에서 닿아야 하는 경로는 `POST /webhooks/github` 하나뿐입니다. `/api/*`와 `/internal/*`은 공개 호스트에서 막아 두세요. 모든 딜리버리는 유효한 `X-Hub-Signature-256`을 실어야 하며, `GITHUB_WEBHOOK_SECRET`이 비어 있는 동안 엔드포인트는 `404`로 응답합니다.

`GITHUB_APP_ID`와 개인 키가 있으면 대시보드가 설치된 저장소와 조직 멤버를 직접 입력하는 대신 제안합니다. 키는 `GITHUB_APP_PRIVATE_KEY_PATH`(파일 — 마운트된 시크릿이 보통 오는 형태)나 `GITHUB_APP_PRIVATE_KEY`(PEM 자체, 원문 또는 base64)로 주고, 둘 다 있으면 경로가 우선합니다. `GITHUB_APP_INSTALLATION_ID`는 선택 사항이며, 없으면 첫 번째 설치를 씁니다. 어느 것도 필수는 아닙니다: 리마인더는 webhook secret만으로 동작하고, 피커는 일반 텍스트 입력으로 되돌아갑니다. 계정 목록은 조직 멤버를 읽는데, 이는 App의 **Organization › Members (read)** 권한이 필요합니다. 없으면 설치된 각 저장소의 assignable 사용자를 대신 제안하고, 대시보드는 어느 목록을 보여주는지 표시합니다.

라우팅은 `data/github-notify.json`에 있습니다: 기본 채널, 저장소별 채널·이벤트 종류 override, GitHub 팀→디스코드 역할 매핑(`teams`). 멘션에 쓰는 GitHub 로그인→디스코드 사용자 연결은 같은 페이지에서 고치지만 대시보드 사용자의 일부로 데이터베이스에 둡니다(`/api/accounts`) — 개인 재생목록과 로그인한 사용자도 이것을 쓰기 때문입니다. 옛 파일의 `accounts`는 첫 시작에서 그쪽으로 옮깁니다. 매핑되지 않은 로그인은 일반 텍스트로 나갑니다. 자기 규칙이 없는 저장소는 기본 채널로 보내되, `notifyUnlistedRepos`를 끄면 목록에 있는 저장소만 보고합니다. 이 기능은 기본 비활성(`enabled: false`)으로 출하됩니다.

리뷰는 사람뿐 아니라 **팀**에도 요청될 수 있습니다. GitHub 페이지의 "팀 → 역할" 카드에서 팀(`org/slug`, org는 저장소 소유자)을 디스코드 역할에 매핑하면, 그 팀에 대한 리뷰 요청은 — webhook으로 오든 `/remind`로 오든 — 역할을 멘션합니다(`<@&role>`). 매핑이 없는 팀은 지금까지처럼 이름만 적고 멘션하지 않습니다. 핑이 실제로 사람들에게 닿으려면 역할이 누구나 멘션할 수 있어야 하거나("Allow anyone to @mention this role"), 봇이 그 채널에서 **Mention Everyone** 권한을 가져야 합니다. 둘 다 아니면 카드가 해당 행에 경고를 띄우고, 역할을 멘션하지 못한 경우 발송 기록에도 그렇게 남습니다. 매핑은 `data/github-notify.json`의 `teams`(`[{ githubTeam, discordRoleId }]`)에 저장되며, 이 키가 생기기 전에 쓰인 파일도 그대로 읽힙니다.

각 이벤트는 같은 페이지에서 구성하는 **임베드**를 보냅니다 — 평문 줄, 제목, 내용, 필드, 꼬리말, 색, 선택적 시간. 모든 부분이 템플릿입니다: `{repo}`, `{pr_number}`, `{pr_url}`, `{pr_title}`, `{event}`, `{actor}`, `{author}`, `{assignee}`, `{assignees}`, `{reviewers}`, `{mentions}`가 치환되고, `{name|있을 때|없을 때}`는 값 유무에 따라 문구를 고릅니다. 비어 있게 렌더되는 부분은 빠집니다. `:name:`으로 친 이모지는 같은 이름의 서버 커스텀 이모지, 없으면 표준 이모지(`:tada:`, `:+1:`, `:white_check_mark:`)로 바뀝니다. 코드와 링크 안은 그대로 둡니다.

조용해진 PR이나 Issue는 **손으로 다시 알릴 수 있습니다** — 디스코드에서 `/remind`, 또는 GitHub 페이지의 "다시 알리기" 카드. 카드는 설치된 저장소 목록에서 저장소를, 이어서 그 저장소의 열린 PR·Issue 목록에서 번호를 고릅니다(`#12 · 제목`, PR·Issue·초안 표시). 닫힌 항목이나 목록을 읽을 수 없는 저장소는 번호를 직접 입력하고("직접 입력…"), App 자격 증명이 없으면 모든 피커가 직접 입력을 제공합니다. 설치된 저장소 중 이름이 하나로 정해지면 이름만 써도 되고(`pipit-bot #12`), PR·Issue 링크도 받습니다. 봇이 App으로 항목을 읽어(여기서부터 `GITHUB_APP_ID`와 개인 키가 필요합니다) 번호가 PR인지 Issue인지 GitHub에서 확인합니다. PR이면 아직 리뷰 요청이 남은 사람과 담당자를 부르는 `PR Reminder`를, Issue면 담당자를 부르는 `Issue Reminder`를 보내며, 작성자는 부르지 않습니다. 리뷰를 요청받은 팀은 매핑된 역할로 멘션하고(위 참고), 매핑이 없으면 이름만 적습니다. 응답은 둘을 합쳐 "Reminded N people or teams"로 셉니다. 초안이거나 기다리는 사람이 없으면 보내지 않고, 머지됐거나 닫힌 항목은 새로 보내지 않되 처음 알림 메시지를 최신 상태로 고칩니다. 사유는 디스코드에 답하고 최근 발송에 남깁니다. 같은 항목은 5분에 한 번만 보냅니다. `PR Reminder`·`Issue Reminder` 이벤트 토글은 이 기능의 허용 스위치입니다 — 기본 켬이고, 저장소에서 끄면 그 저장소에서는 그 종류를 다시 알리지 않습니다.

이벤트가 제공하는 변수는 그 이벤트가 채울 수 있는 것에 따라 다릅니다 — `{actor}`는 머지에서는 머지한 사람, 리뷰에서는 리뷰어이고, `{reviewers}`(아직 남은 요청 목록)는 GitHub가 이미 비운 자리에서는 제공되지 않습니다. 편집기는 편집 중인 이벤트의 변수를 나열하고, 다른 변수를 쓴 템플릿은 저장이 거부됩니다. 이벤트마다 기본값이 있고, 편집하지 않은 이벤트는 그것을 따릅니다.

멘션은 평문 줄에 둡니다: 임베드 안에만 있는 멘션으로는 디스코드가 알림을 울리지 않습니다. 템플릿은 운영자가 쓴 마크다운 그대로지만 치환되는 값은 전부 이스케이프되므로, PR 제목으로 멘션이나 링크를 위조할 수 없습니다.

PR이나 이슈를 알린 메시지는 데이터베이스에 기억됩니다(상한 있음, 오래된 것부터 삭제). 나중에 누군가 배정되거나 리뷰 요청을 받으면 — 또는 배정이 해제되거나 제목이 바뀌면 — 그 메시지를 현재 제목·담당자·리뷰어로 다시 그려 제자리에서 수정하므로 낡지 않습니다. PR이나 이슈를 재오픈하면 다시 알리고, 그 메시지가 이후 최신 상태를 유지하는 메시지가 됩니다. 자기 자신을 배정하면 수정만 합니다 — 새 메시지도, 핑도 없습니다. 다른 사람을 배정하거나 리뷰를 요청하면 메시지를 수정하고 그 이벤트의 메시지도 보냅니다. 수정으로 생긴 멘션에는 디스코드가 알림을 주지 않기 때문입니다. 봇이 추적을 시작하기 전에 알려진 항목이나 메시지가 삭제된 항목은 수정하지 않습니다. 새로 게시한 것 없이 갱신만 한 경우 최근 발송 결과에 `edited`로 표시됩니다.

디스코드 개발자 포털에서 **Server Members Intent**를 켜세요. 봇에는 `Manage Roles`, `Send Messages`, `Add Reactions`, `View Channel`, `Read Message History`, `Manage Guild`(초대 사용 횟수)가 필요합니다. 봇 역할은 부여하는 역할보다 위에 있어야 합니다.

## 초대

초대 페이지에서 채널 두 개를 정합니다. **안내 채널**에는 직접 쓴 입장·퇴장 메시지가 갑니다(`{user}`, `{username}`, `{inviter}`, `{invite}`; 여러 개면 무작위로 하나). **기록 채널**은 선택이며 따로 정하고, 입장·퇴장마다 사실만 담은 한 줄 — 누가, 어떤 초대로, 누가 만든 초대인지, 나간 사람은 며칠 머물렀는지 — 이 남습니다. 알림은 가지 않습니다.

유입은 초대 코드별로 데이터베이스에 세므로, 초대가 사라져도 수는 남습니다. "초대 코드별 유입" 카드는 초대마다 만든 사람, 봇이 센 유입 수, 디스코드의 사용 수, 최근 유입, 만료·사라짐 여부를 보여 줍니다. 새 멤버가 어떤 초대로 들어왔는지 알려면 **Manage Guild**(서버 관리) 권한이 필요합니다. 없으면 디스코드가 초대 목록은 보여 줘도 사용 횟수를 빼고 보내서, 어떤 초대인지 알 수 없고 아무것도 세어지지 않습니다 — 그럴 때 카드가 경고합니다.

## 감사 로그

봇은 누가 무엇을 했고 결과가 어땠는지 남깁니다:

- 대시보드에서 바꾼 것(설정, 음악 조작, 리액션 롤 패널, 다시 알리기 등) — 요청 본문은 남기지 않습니다
- 디스코드의 슬래시 명령, 리모컨 버튼과 재생 입력 창, 음악 채널에 친 요청. 보기만 하는 명령(`/queue`, `/help`)은 남기지 않습니다
- 음악 작업이 어떻게 끝났는지(출처, 실패했으면 실패 코드). 자동 재생으로 봇이 넣은 곡은 사용자가 `pipit-bot`입니다
- GitHub 발송(보냄·수정·건너뜀·실패와 사유), 멤버 입장(초대 코드·초대한 사람)·퇴장
- 기능을 켜고 끈 기록에는 어떤 기능을 어느 쪽으로 바꿨는지가 함께 남습니다(막힌 시도도 마찬가지)

결과는 네 가지입니다: **성공** · **권한 없음**(쓰기 권한이 없는 대시보드 계정의 요청을 막음) · **오류** · **건너뜀**.

**음악은 누가 어떤 기능을 썼는지만** 남깁니다 — 곡도, 요청한 내용도 남기지 않습니다 — 운영자가 **음악 요청 기록**(설정 페이지의 감사 로그 카드, `data/audit-settings.json`)을 켜지 않는 한. 켜면 그때부터 음악 작업 기록마다 요청한 내용과 준비된 곡 제목이 함께 남습니다. 이미 남은 기록은 바뀌지 않고, 끄면 다시 기능 사용만 남습니다. 기록은 데이터베이스에 두고 **90일**이 지나면 지웁니다. v0.8.0 전에 쓰던 하루 파일(`data/audit/YYYY-MM-DD.jsonl`)은 첫 시작에서 뒤에서 옮기고 `*.migrated`로 남깁니다. 기록에는 디스코드 사용자 ID·표시 이름과 대시보드 사용자 이름이 들어가므로, 데이터베이스를 읽을 수 있는 사람을 생각해 두세요. 대시보드 **로깅** 페이지에서 분류·기간·검색으로, 한 페이지 5·10·20·30줄씩 번호 페이지로 봅니다. 표는 시각·기능·수행 작업·사용자·대상 · 내용·결과 순이고, 시각은 보는 사람의 시간대로 `2026.10.20. 15:04:05`처럼 적힙니다.

## 리액션 롤

**패널**은 봇이 소유한 메시지 하나입니다. 채널을 고르고, 임베드를 구성하고, 어떤 이모지가 어떤 역할을 주는지 나열합니다. 발행하면 메시지를 보내고 각 이모지로 반응을 붙입니다. 패널을 수정해 다시 발행하면 같은 메시지를 고치고 반응을 옵션에 맞춰 다시 정리합니다.

패널은 **반응 수 1**로 유지할 수 있습니다 — 봇이 멤버의 반응을 즉시 떼어내므로 메시지가 집계가 아니라 버튼 줄처럼 읽히고, 이모지를 누를 때마다 역할이 켜지고 꺼집니다. 끄면 반응 자체가 기록입니다: 붙이면 역할 부여, 떼면 회수.

봇은 보내기 전에 검사합니다: 그 채널에서 글을 쓰고 반응할 수 있어야 하고, 모든 역할이 봇 역할보다 아래에 있어야 하며 디스코드가 관리하는 역할이 아니어야 합니다. 반응 수 1 유지에는 `Manage Messages`도 필요하고, 가운데에 이모지를 끼워 넣은 뒤 순서를 되돌리는 데도 필요합니다 — 디스코드는 반응이 처음 붙은 자리를 고정하므로, 유일한 수리 방법은 전부 지우고 다시 반응하는 것입니다. 역할을 줄 수 없는 패널은 멤버가 반응했을 때 조용히 실패하는 대신 사유와 함께 발행이 거부됩니다. 패널은 데이터베이스에 저장됩니다(옛 `data/reaction-roles.json`은 첫 시작에서 옮깁니다).

## 음악

음악 명령으로 하는 일은 대시보드 **음악** 페이지에서도 할 수 있습니다:

- **통화방** — 통화방을 고르면 봇이 참여하고, 연결된 상태에서 다른 방을 고르면 지금 곡을 멈추지 않고 옮겨 갑니다. 피커에 방마다 인원이 보입니다 — 아무도 없는 방은 30초 뒤 봇이 스스로 나가기 때문입니다. **나가기**로 연결을 끊습니다
- **대기열** — 대기 중인 곡 전체(최대 100곡 표시)와 곡마다 **위로**·**아래로**·**여기로 건너뛰기**·**빼기**(휴대폰에서는 메뉴 하나로), 그리고 대기 중인 곡을 한 번 섞는 **섞기**. 행은 플레이어의 트랙 id로 지정하므로 목록이 잠깐 늦어도 다른 곡을 건드리지 않습니다. 건너뛰면 앞의 곡들은 `/skip to`처럼 빠집니다
- **최근 재생** — 이번 세션에서 재생한 곡(최근 20곡)과 **이전 곡**. 이전 곡으로 가면 지금 곡은 대기열 맨 앞으로 돌아갑니다. 기록은 세션이 끝나면 사라집니다
- **추가** — 입력한 쿼리를 그대로 music worker에 보냅니다. 메뉴의 **다음에 재생**은 `/play next`처럼 대기열 맨 앞에 넣습니다
- **검색** — music worker의 결과를 최대 5개 보여 주는 창을 엽니다. 결과마다 **추가**하거나 **다음에 재생**으로 넣을 수 있고, 여러 곡을 이어서 넣을 수 있습니다. 봇이 통화방에 들어가기 전에도 검색은 되고, 추가는 들어간 뒤에 됩니다
- **볼륨** — 0–200을 1단위로 맞추는 슬라이더와 숫자 칸. 100이 준비된 원래 크기이고, 넘으면 키웁니다(큰 소리는 깨질 수 있음). 통화방에 있든 없든 언제든 바꿀 수 있습니다
- **재생 옵션** — **모노**는 좌우 소리를 합쳐 양쪽에 똑같이 내보냅니다(이어폰 한쪽으로 들을 때). 재생 중인 곡에도 바로 적용되고, 봇이 통화방에 없어도 바꿀 수 있습니다. **자동 재생**은 음악이 끊기지 않게 합니다: 대기열의 마지막 곡이 시작되면 봇이 music worker에게 이어 들을 곡을 받아 준비하고, 그 곡이 끝나기 10초 전에 대기열에 넣습니다 — 그 사이 누가 곡을 넣으면 그 곡이 먼저입니다. 반복이 켜져 있거나 재생목록을 재생하는 동안은 쉬고, 다음 곡 추천을 지원하는 music worker가 필요합니다([docs/music-backend.md](./docs/music-backend.md)). 볼륨·모노·자동 재생은 `data/playback-options.json`에 저장되어 재시작해도 유지됩니다

대시보드, 배너, 명령은 같은 대기열을 씁니다. 어느 쪽에서든 이어서 조작할 수 있습니다.

### 음악 채널

설정된 음악 채널에는 **리모컨 배너**가 하나 있고, 봇이 채널의 마지막 메시지로 유지합니다:

- **대기 화면** — "💿 Pipit Hub Music", 곡을 요청하는 방법, 곡 제목이나 링크를 입력하는 창을 여는 **재생** 버튼, **검색**, **재생목록**, **통화방 참여**, **관제 센터** 링크
- **재생 중 화면** — 곡, 신청한 사람, 진행 막대, 반복·볼륨·대기열, 그리고 일시정지/재개·다음·정지·대기열·재생목록·곡 추가·검색·반복·볼륨 10씩 낮추기/높이기·모노·자동 재생·통화방 참여 버튼과 **관제 센터** 링크. 버튼의 결과는 누른 사람에게만 5초 동안 보입니다
- **통화방 참여**는 `/join`처럼 누른 사람의 통화방으로 봇을 부릅니다 — 다만 다른 통화방에서 재생 중인 세션은 옮기지 않습니다. 옮기려면 `/join`이나 대시보드를 쓰세요
- **관제 센터** 링크는 대시보드의 음악 페이지를 엽니다([환경 변수](#환경-변수)의 `DASHBOARD_URL` 참고). 주소를 알 수 없으면 빠집니다
- 채널에 **곡 제목이나 링크를 치면** 재생합니다: 그 줄은 지워지고, 모두에게 보이는 짧은 배너가 결과를 알린 뒤 스스로 사라집니다. 줄을 지우려면 그 채널에서 봇에게 **메시지 관리** 권한이 필요합니다. 없으면 요청은 그대로 처리되고 줄만 남습니다

**검색** — `/search`나 배너의 검색 버튼 — 은 결과를 최대 5개, 검색한 사람에게만 보여 줍니다. 하나를 골라 바로 재생하거나 다음 곡으로 넣습니다. 결과는 10분 동안, 검색한 사람만 고를 수 있습니다. 검색을 지원하는 music worker가 필요하고([docs/music-backend.md](./docs/music-backend.md)), 지원하지 않으면 봇이 그렇게 알려 주고 나머지는 그대로 동작합니다.

배너는 봇이 시작하거나 음악 채널이 추가될 때 게시되고, 지워지면 다시 게시되며, 음악 채널에서 빠진 채널에서는 사라집니다.

**music worker가 꺼져 있으면** 배너가 그렇게 알립니다: 대기 중에는 곡을 요청하는 방법 대신 지금은 곡을 준비할 수 없다는 안내를, 재생 중에는 곡은 그대로 두고 새 곡을 준비할 수 없다는 한 줄을 보여 줍니다. 그동안 worker가 필요한 버튼 — 재생·곡 추가·검색·재생목록·자동 재생 — 은 비활성이고, 나머지는 그대로 쓸 수 있습니다. 채널에 새 메시지는 남기지 않고, worker가 돌아오면 배너는 저절로 평소로 돌아갑니다. 꺼진 동안에도 요청은 보내며 — 그때도 꺼져 있으면 답이 그렇게 말합니다 — 대시보드의 음악 페이지도 같은 안내를 얼마나 됐는지와 함께 보여 줍니다. 봇이 어떻게 아는지는 [docs/music-backend.md](./docs/music-backend.md)를 참고하세요.

### 재생목록

재생목록은 음악 페이지의 **재생목록** 탭과 `/playlist`에 있습니다:

- **공용** 재생목록은 서버 모두가 보고 누구나 고칠 수 있고, **개인** 재생목록은 주인만 보고 고칩니다. 대시보드에서 개인 재생목록을 쓰려면 GitHub 페이지의 계정 연결에 내 GitHub ↔ 디스코드가 있어야 합니다(대시보드 로그인 = GitHub)
- **곡 담기** — 곡 제목이나 링크를 입력하거나, 지금 곡·대기열 곡·대기열 전체·최근 재생·검색 결과 옆의 "재생목록에 담기"(대시보드와 디스코드 검색 결과), 또는 music worker가 여러 곡으로 풀 수 있는 **링크에서 가져오기**(worker가 지원할 때만 보임, [docs/music-backend.md](./docs/music-backend.md))
- **재생** — 차례로 또는 섞어서, 지금 대기열 뒤에. 봇은 music worker에 두 곡씩 요청하고 재생목록 순서를 지킵니다. 준비하지 못한 곡은 건너뛰고 셉니다. 정지·비우기·나가기·다른 재생목록 재생은 지금 재생목록을 멈춥니다
- 음악 채널 리모컨에 **재생목록** 버튼 — 고르고 재생 또는 섞어서 재생
- 상한: 재생목록 200개, 재생목록마다 300곡. 재생목록은 곡의 요청 값까지 데이터베이스에 보관하고, 화면과 답에는 제목만 보입니다

### 음악 작업

요청 하나하나는 music worker가 준비한 뒤에야 재생되는 **작업**입니다. **음악 작업** 카드가 상태와 함께 5개씩 페이지로 보여 줍니다:

- 준비 중인 작업은 **취소**할 수 있습니다 — 봇이 기다리기를 멈추고, 나중에 파일이 와도 재생하지 않습니다
- 실패했거나 취소한 작업은 같은 요청으로 **다시 시도**할 수 있습니다("다음에 재생"이었다면 그대로 맨 앞). 찾을 수 없음처럼 다시 해도 안 될 실패에는 버튼이 없습니다
- 실패에는 이유가 표시됩니다 — worker가 짧은 코드를 함께 보낼 수 있습니다([docs/music-backend.md](./docs/music-backend.md) 참고). 너무 오래 걸리는 작업은 끝없이 기다리지 않고 시간 초과로 실패합니다
- 대기열에서 기다리는 동안 준비된 파일이 사라진 곡은 건너뛰고, 음악 채널과 대시보드에 알립니다

### 음악 결산

재생된 곡은 모두 기록됩니다 — 곡, 실제로 재생한 시간, 끝난 방식, 직접 요청·재생목록·자동 재생 중 어디서 왔는지 — 그리고 **400일** 동안 남습니다. **누가 어떤 곡을 신청했는지는 어떤 화면에도 나오지 않습니다**: 요청한 사람은 본인 결산을 위해서만 저장됩니다([결정 025](./docs/decisions/025_v0.8.1_music-recap.md)). 요청한 내용은 재생 기록에 남지 않습니다.

- **결산** — 재생 시간, 재생 수, 곡 수, 참여 인원, 많이 들은 곡, 요일별·시간대별 재생, 자동 재생 비중, 연 결산은 월별 추이까지. 끝까지, 또는 곡의 절반 이상(길이를 모르면 1분) 들은 것을 "들었다"로 셉니다
- **디스코드** — 게시를 켜면 매월 1일에 지난달, 1월 1일에 지난해 결산을 결산 채널에 올립니다. 봇이 꺼져 있어 놓친 달·해는 시작할 때 올리고, 재생이 없던 기간은 올리지 않습니다
- **연말 재생목록** — 연 결산과 함께 그 해 많이 들은 곡으로 공유 재생목록 "2026 결산"이 만들어집니다
- **대시보드** — **음악 결산** 페이지에서 달·해별 결산(진행 중인 기간은 지금까지의 집계)과 **내 결산**(GitHub ↔ 디스코드 연결로 찾은 내 재생)을 봅니다. 관리자는 끝난 기간을 다시 게시할 수 있습니다
- **`/recap [period]`** — 내 결산을 나에게만, 내 디스코드 언어(한국어·영어)로 보여 줍니다
- **설정** — 설정 페이지의 음악 결산 카드, `data/music-recap.json`: 재생 기록(켬), 게시(끔), 채널, 기간 기준 시간대(`Asia/Seoul`), 순위 곡 수(10). 채널에 올리는 결산의 언어는 언어 설정입니다([언어](#언어) 참조). v0.8.3 전에 여기서 고른 언어는 한 번 옮겨집니다. 결산은 v0.8.1부터 쌓인 기록만 다룹니다

## 기능별 켜고 끄기

**설정** 페이지에서 일곱 기능을 켜고 끕니다: 음악, GitHub 알림, 감사 로깅, 초대 추적, 입장·퇴장 메시지, 입장 역할, 리액션 롤. `data/features.json`이 없으면 지금처럼 전부 켜져 있고, GitHub 스위치는 GitHub 페이지의 전체 스위치와 같습니다.

끄면 어디서나 꺼집니다:

- **명령** — 꺼진 기능의 슬래시 명령(음악 명령들, GitHub은 `/remind`)이 디스코드 목록에서 사라지고, 켜면 돌아옵니다. 디스코드에 반영되는 데 잠시 걸릴 수 있습니다. `/help`는 켜진 것만 보여 줍니다
- **음악** — 끄면 재생을 멈추고 통화방에서 나갑니다. 음악 채널 배너는 꺼져 있다고 알리고, 채널 메시지는 건드리지 않습니다
- **나머지** — 감사 로깅이 꺼진 동안은 기록하지 않습니다(끈 사실은 남음). 초대 추적을 끄면 초대 매칭·집계·기록 채널이 멈추고, 입장·퇴장 메시지와 입장 역할은 건너뛰며, 리액션 롤 패널에 반응해도 아무 일도 없습니다
- **대시보드** — 꺼진 기능의 페이지도 열리되 위에 안내와 설정 링크가 붙고, 사이드바 항목이 흐려집니다

## 소스 추상화

이 저장소는 음악 백엔드를 외부 **music worker**로만 설명합니다 — 특정 소스도, 워커의 이름도 언급하지 않습니다. [docs/music-backend.md](docs/music-backend.md)의 계약이 인터페이스의 전부입니다.

`yarn check:abstraction`이 이를 강제합니다. pre-commit 훅이 스테이징된 파일을, commit-msg 훅이 메시지를, **Source Abstraction** 워크플로가 푸시된 범위 전체를 검사합니다 — 마지막 것은 `--no-verify`로 건너뛸 수 없는 검사입니다.

## 개발

`pipit-bot/`에서:

```sh
yarn install
yarn watch:start
```

대시보드(Vite + Vue)는 `dashboard/`에서:

```sh
yarn dashboard:dev
```

`http://127.0.0.1:5173/`이 열리고 `/api`는 봇으로 프록시됩니다. 프로덕션에서는 `yarn dashboard:build` 후 봇이 `dashboard/dist`를 `GET /`에서 서빙합니다.

`yarn watch:start`에는 `DATABASE_HOST` 등(`.env.development.local`)으로 가리킨 PostgreSQL이 필요합니다 — compose 스택의 것이나 로컬의 아무것이나.

전체 스택(봇 + music worker + PostgreSQL)은 저장소 루트의 워크스페이스 compose를 씁니다:

```sh
docker compose -f docker-compose.yaml -f docker-compose.dev.yaml up --build
```

개발용 스트림은 `../shared/`에 저장됩니다.

## 명령

모든 명령은 **슬래시 명령**입니다(v0.7.1부터) — 디스코드에서 `/`를 치면 목록이 보입니다. 명령 접두사는 더 이상 없습니다. 답은 명령을 쓴 사람에게만 보입니다.

- `/remind item` — `owner/name #12`, `name #12`, 또는 PR·Issue 링크. PR이나 Issue가 기다리는 사람을 저장소의 알림 채널에서 다시 부릅니다. 위 리마인더 절 참고
- `/help` — 명령 목록 · `/ping` — 봇이 답하는지 확인

### 음악 명령

음악 채널에서 쓸 수 있습니다(음악 채널이 없으면 어디서나):

- `/play query [next]` — 쿼리를 그대로 music worker로 전달. `next`는 대기열 맨 앞에 넣음
- `/search query` — 결과 최대 5개를 나에게만 보여 줌. 골라서 바로 재생하거나 다음 곡으로
- `/playlist` — `list`, `show`, `create [personal]`, `rename`, `delete`, `add`(지금 곡·대기열 전체·제목이나 링크), `remove`, `move`, `import link [into]`, `play [shuffle]`. 재생목록 이름은 자동완성
- `/join`, `/leave` — 내가 있는 통화방에 참여(또는 이동), 또는 나가기
- 재생: `/pause`, `/resume`, `/skip [to]`, `/stop`, `/back`, `/loop mode`, `/volume [0–200]`
- 옵션: `/options [mono] [autoplay] [repeat]` — 모노·자동 재생을 켜고 끄거나, 새 세션의 반복 모드를 정하거나, 재생 옵션을 봅니다
- 대기열: `/queue`, `/remove position`, `/move from to`, `/shuffle`, `/clear`
- `/recap [period]` — 내 음악 결산(이번 달·지난달·올해·작년). 음악 채널 밖에서도 됩니다

대시보드 음악 페이지와 음악 채널의 배너에서도 같은 조작을 할 수 있습니다([음악](#음악) 참고). 봇은 쿼리 문자열을 검증하거나 파싱하지 않습니다.

### `!` 명령에서 올라올 때

슬래시 명령을 쓰려면 봇이 **`applications.commands`** scope로 초대되어 있어야 합니다: Discord Developer Portal에서 앱 → OAuth2 → URL Generator를 열고 `bot`과 `applications.commands`를 체크한 뒤 봇 권한을 골라, 나온 URL로 서버에 다시 승인하세요 — 봇을 내보낼 필요는 없습니다. 음악 채널을 깔끔하게 유지하려면 그 채널에서 봇에게 **메시지 관리** 권한을 주세요(채널 편집 → 권한 → 봇 역할).
