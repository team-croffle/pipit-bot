# Release notes — `.ai/release/`

`.ai/release/pipit-bot_v<version>_release.md` holds the **release note body** posted to the GitHub Release — the
exact text passed to `gh release edit --notes-file`. Not a procedure document. Written in Korean and English with the same
content. The notes are public: `AGENTS.md` §2 applies to every line.

## Titles

| Kind        | GitHub Release title      | File                               |
| ----------- | ------------------------- | ---------------------------------- |
| Stable      | `Release vX.Y.Z`          | `pipit-bot_vX.Y.Z_release.md`      |
| Pre-release | `Pre-Release vX.Y.Z-rc.A` | `pipit-bot_vX.Y.Z-rc.A_release.md` |

Headings inside the note use `Pipit Hub vX.Y.Z`.

## Changelogs section

The last section of the English block is `## Changelogs`, generated by GitHub:

```
gh api -X POST repos/team-croffle/pipit-bot/releases/generate-notes \
  -f tag_name=vX.Y.Z[-rc.A] -f previous_tag_name=<previous tag> --jq .body
```

Paste it as is, renaming `## What's Changed` to `## Changelogs`. `previous_tag_name`: the previous tag in semver order for
an rc; the previous **stable** tag for a stable release (so the list spans every rc). The Korean block says `- 하단 참조`.

## Writing rules

- Order: what the operator must act on (breaking changes, env, permissions) → changes by feature → upgrade steps.
- Describe behaviour, not files. PR numbers are fine (`#10`).
- Changes and explanations only: no verification requests, work status, commands, run URLs or QA logs — those belong in
  `.ai/history/` and `.ai/test/`.
- `<summary>` must be followed by a blank line and `</details>` preceded by one, or the inner markdown does not render.
