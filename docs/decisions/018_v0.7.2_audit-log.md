### 맥락

누가 설정을 바꿨는지, 누가 음악을 멈췄는지, PR 알림이 왜 안 왔는지 — 지금까지는 서버 로그를 뒤지거나 최근 몇 개만 남는 메모리 목록을
봐야 했습니다. 데이터베이스는 v0.8 계획이라, 그 전에 쓸 수 있는 기록이 필요했습니다. 팀은 음악에 대해서는 **누가 어떤 기능을 썼는지만**
알면 되고, 어떤 곡이었는지는 필요 없다고 정했습니다.

### 결정

- 기록 한 줄은 `{ at, category, action, actor, target, outcome, detail }`. 분류는 대시보드·음악·명령·GitHub·멤버.
- `data/audit/` 아래 **하루 파일 하나**(`YYYY-MM-DD.jsonl`, UTC)에 한 줄씩 덧붙이고, **90일**이 지난 파일은 지웁니다. 쓰기는 하나씩
  차례로, 실패해도 기록하려던 동작은 막지 않습니다.
- **기능마다 기록하지 않고, 모든 조작이 지나가는 가장자리 네 곳에서 기록합니다**: 대시보드 쓰기 요청 뒤의 미들웨어, 모든 interaction에
  답하는 `replyNotice`, GitHub 발송 결과를 남기는 `recordDelivery`, 멤버 입장·퇴장 리스너. 새 기능도 같은 길로 지나가면 자동으로
  기록됩니다.
- 음악은 행동·사람·결과만. 답 문장(곡 제목이 들어감), 명령 옵션 값, 요청 본문, music worker의 오류 문장은 남기지 않습니다. 곡 준비
  결과는 출처와 실패 코드만. 보기만 하는 명령(`/queue`, `/help`)은 기록하지 않습니다.
- 대시보드 "로깅" 페이지가 분류·기간·검색으로 읽습니다.

### 결과

- 데이터베이스 없이도 90일 동안 무슨 일이 있었는지 볼 수 있고, v0.8에서는 같은 형태를 그대로 옮기면 됩니다.
- 음악 기록이 곡을 담지 않으므로, 월말·연말 음악 결산(v0.8.1)은 이 로그가 아니라 따로 설계해야 합니다.
- 기록은 사용자 ID와 표시 이름을 담습니다 — 보관 기간과 위치를 README에 적었습니다.

## Context

Who changed a setting, who stopped the music, why a pull request was never announced — so far the answer meant reading
server logs or a short in-memory list that kept only the latest few. A database is planned for v0.8; a record was needed
before then. For music the team decided it needs to know **only who used which feature**, never which track.

## Decision

- One entry is `{ at, category, action, actor, target, outcome, detail }`; categories are dashboard, music, command,
  GitHub and member.
- Entries are appended to **one file per day** under `data/audit/` (`YYYY-MM-DD.jsonl`, UTC), and files older than
  **90 days** are removed. Writes happen one at a time; a failed write never blocks the action being recorded.
- **Recording happens at four edges every action already passes**, not inside each feature: a middleware after every
  dashboard write, `replyNotice` (which answers every interaction), `recordDelivery` (GitHub results) and the member
  join and leave listeners. A new feature that goes through the same paths is recorded without extra code.
- Music keeps the action, the person and the outcome only. The answer text (which names the track), command option
  values, request bodies and the music worker's error text are never recorded; a finished job keeps its origin and
  failure code. Commands that only show something (`/queue`, `/help`) are not recorded.
- The dashboard's logs page reads it, filtered by category, period and text.

## Consequences

- Ninety days of what happened are visible without a database, and v0.8 can move the same shape into one.
- Because music entries carry no track, the monthly and yearly music summary (v0.8.1) needs its own design rather than
  this log.
- Entries hold Discord user ids and display names; the README states where they are kept and for how long.
