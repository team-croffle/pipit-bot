# 005 — Releases are cut by a workflow, tested as pre-releases

<details>

- **버전:** v0.5.0
- **상태:** 채택

### 맥락

봇은 컨테이너 이미지로 배포되고, 기능이 자리 잡는 동안에는 한 주에 여러 번 배포되기도 합니다. 손으로 태그를 달고 빌드하다 보니
버전이 `package.json`과 어긋났고, 개발자 컴퓨터에서만 확인한 변경이 곧바로 팀 서버로 갔습니다.

### 결정

- 버전을 매기는 방법은 **릴리즈 워크플로**(`workflow_dispatch`) 하나뿐입니다. `package.json`을 올리고, 태그를 달고, 이미지를
  빌드해 올리고, 릴리즈 초안을 만듭니다. 손으로 태그를 달지 않습니다.
- 작업은 먼저 실제 서버에서 시험할 만큼의 변경을 묶은 **프리릴리즈**(`vX.Y.Z-rc.N`)로 나가고, 프리릴리즈가 확인되면 정식
  `vX.Y.Z`가 뒤따릅니다. 프리릴리즈는 `latest` 이미지를 옮기지 않습니다.
- PR은 **rebase로만** 머지해서 `master`를 한 가지 목적의 커밋들로 이어진 한 줄로 유지합니다.

### 결과

- 실행 중인 모든 이미지가 태그 하나, 릴리즈 노트 하나에 대응합니다(두 언어, 자동 생성 변경 목록 포함. 정식 노트는 포함된
  프리릴리즈를 나열).
- 릴리즈는 입력값을 분명히 한 디스패치 한 번입니다. 버전을 건너뛰려면 버전을 직접 넘깁니다.
- 핫픽스도 워크플로를 거치므로 기록은 정직하지만 "고쳐서 바로 올리기"는 느려집니다.

## Context

The bot is deployed as a container image, often several times a week while a feature settles. Tagging and building by
hand made versions drift from `package.json`, and a change that was only checked on a developer machine went straight to
the team's server.

## Decision

- A **release workflow** (`workflow_dispatch`) is the only way to version: it bumps `package.json`, tags, builds and
  pushes the image, and drafts the release. Nobody tags by hand.
- Work ships first as **pre-releases** (`vX.Y.Z-rc.N`) that bundle enough change to test on the real server; a stable
  `vX.Y.Z` follows once the pre-releases are confirmed. A pre-release never moves the `latest` image.
- Pull requests merge by **rebase only**, so `master` stays a line of single-purpose commits.

## Consequences

- Every running image maps to a tag and a release note (bilingual, with the generated changelog; a stable note lists
  the pre-releases it includes).
- Releasing is one dispatch with explicit inputs; skipping versions means passing the version explicitly.
- A hotfix still goes through the workflow, which keeps history honest but makes "just push a fix" slower.
