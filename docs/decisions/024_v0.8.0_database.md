### 맥락

모든 것이 `data/` 아래 JSON 파일이었습니다. 추적 메시지는 상한을 두고 오래된 것을 버려야 했고, 감사 로그는 날짜 파일을
처음부터 훑어야 조회됐습니다. 앞으로 투표·일정·결산처럼 같은 데이터를 여러 곳에서 읽고 기간으로 집계하는 기능이 옵니다.

### 결정

- **엔진은 PostgreSQL 하나입니다.** `DATABASE_HOST`·`PORT`·`USERNAME`·`PASSWORD`·`NAME`(또는 `DATABASE_URL` — rc.4부터)으로 붙고, compose에 `postgres:16-alpine` 서비스가 있습니다. 이미 컨테이너 스택인
  제품이라 컨테이너가 하나 느는 것은 새 부담이 아닙니다. SQLite와 동시 지원은 하지 않습니다 — 스키마·마이그레이션·검증이 두 벌이 됩니다.
- **ORM은 drizzle입니다.** 네이티브 바이너리가 없고, 스키마가 TypeScript이고, 마이그레이션이 평문 SQL(`drizzle/`)이라 PR에서 읽힙니다.
  봇이 시작할 때 적용합니다.
- **가르는 기준**: 봇이 만들어 내는 식별자·상태와 계속 쌓이는 것은 DB, 사람이 열어 고치는 설정은 파일. 설정을 파일로 두는 이유는
  복구 경로입니다 — 대시보드에 들어갈 수 없을 때 편집기로 고치고 다시 시작할 수 있어야 합니다.
- **저장소는 메모리 캐시 + 즉시 저장입니다.** 시작할 때 행을 메모리로 읽어 두고, 바뀐 것은 바로 DB에 씁니다. 읽는 코드가 동기
  그대로라 바뀌는 범위가 저장소 모듈 안에 머뭅니다. 기능 코드는 드라이버를 직접 만지지 않습니다.
- **이주는 시작할 때 한 번**: 파일을 옮기고 이름을 `*.migrated`로 바꿉니다(지우지 않음 — 되돌릴 수 있게). 기록 표가 있어 두 번 넣지 않습니다.
- **감사 로그는 캐시 없이 SQL로 바로 조회**합니다(v0.8.0-rc.2) — 계속 쌓이고, 기간·분류·글자로 찾기 때문입니다. 옛 하루 파일은 하루씩 뒤에서 옮깁니다.
- **데이터베이스에 둔 것**(v0.8.0): 추적 메시지, 배너, 초대 통계, 감사 로그, 재생목록, 리액션 롤 패널(게시한 메시지 ID가 붙어 있어 통째로),
  GitHub ↔ 디스코드 계정 연결(설정이 아니라 신원 — 자기 API `/api/accounts`). **파일로 남긴 것**: 운영 설정, 기능 스위치, 입장·퇴장 설정,
  GitHub 알림 설정(계정 연결 제외), 재생 옵션, 감사 설정.
- 이미 옮긴 파일이 다시 나타나면(이전 이미지가 돌았던 경우) 다시 옮기지 않고 시각 붙은 이름으로 치워 두며 그렇다고 로그에 남깁니다 — 데이터베이스가 기록입니다.

### 결과

- 백업이 두 곳(DB + `data/`)이 됩니다. 되돌리기는 이전 이미지 + `*.migrated` 이름 되돌리기입니다.
- "DB가 없다"는 새 장애 유형이 생깁니다. 시작할 때는 최대 2분 기다리고, 그래도 없으면 시작하지 않습니다.
- 메모리 캐시는 봇 프로세스 하나를 전제로 합니다. 두 번째 프로세스가 같은 데이터를 쓰게 되면 캐시를 맞추는 장치가 필요합니다
  — 그때 이 결정을 다시 봅니다.

## Context

Everything was a JSON file under `data/`. Tracked messages needed a cap that dropped the oldest; the audit log could only
be queried by reading day files from the start. Features ahead — polls, schedules, monthly summaries — read the same data
from more than one place and aggregate it over periods.

## Decision

- **One engine: PostgreSQL**, reached through `DATABASE_HOST`, `PORT`, `USERNAME`, `PASSWORD` and `NAME` (or a `DATABASE_URL`, from rc.4); the compose stack runs a `postgres:16-alpine` service. The
  product already ships as a container stack, so one more container is not a new burden. No SQLite alongside it — that
  would double the schema, the migrations and the checks.
- **drizzle as the ORM**: no native binaries, a TypeScript schema, and plain SQL migrations (`drizzle/`) that read well in
  a pull request. The bot applies them when it starts.
- **Where the line falls**: identifiers and state the bot produces, and anything that keeps growing, go to the database;
  settings a person opens and edits stay files. Settings stay files for the way back in — when the dashboard is locked
  out, they can be fixed in an editor and the bot restarted.
- **Stores keep their rows in memory and write through.** Rows are loaded at start-up and every change goes straight to
  the database. The code that reads them stays synchronous, so the change stays inside the storage modules. Feature code
  never touches the driver.
- **Moving in happens once, at start-up**: a file is moved in and renamed to `*.migrated` (not deleted, so going back
  stays possible); a record table keeps it from being moved twice.
- **The audit log is queried in SQL, with no in-memory copy** (v0.8.0-rc.2): it keeps growing and is searched by period,
  category and text. Its old day files are moved in a day at a time, in the background.
- **In the database** (v0.8.0): tracked messages, banners, invite counts, the audit log, playlists, reaction-role panels
  (whole — a published one carries the id of the message the bot posted) and the GitHub ↔ Discord account links
  (identity rather than a setting, with their own `/api/accounts`). **Still files**: the bot's settings, feature switches,
  join and leave settings, GitHub notification settings (without the links), playback options, audit settings.
- A file that turns up again after it was moved in (an older image ran in between) is not moved in again: it is set
  aside under a timestamped name and the log says so — the database is the record.

## Consequences

- Backups cover two places, the database and `data/`. Going back is the older image plus renaming the `*.migrated` files.
- "The database is not there" is a new failure. At start-up the bot waits up to two minutes and otherwise does not start.
- The in-memory copies assume one bot process. Once a second process writes the same data, the copies need keeping in
  step — that is when to revisit this decision.
