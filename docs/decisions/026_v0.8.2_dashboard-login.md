# 026 — The dashboard signs people in itself, and admin is a group

<details>
<summary><b>한국어 — 대시보드가 직접 로그인을 맡고, 관리자는 그룹이다</b></summary>

- **버전:** v0.8.2
- **상태:** 채택

### 맥락

대시보드는 들어오자마자 OIDC 제공자로 보냈습니다. 흐름은 `openid-client`로 직접 엮었고, 세션은 그룹을 담은 서명 쿠키였습니다.
제공자가 없는 운영은 들어올 방법이 없었고, 개발 환경은 로그인 없이 env로 정한 신원을 썼습니다. 팀은 로그인 화면, 켜고 끌 수 있는
여러 로그인 방법(비밀번호 · OIDC · Discord · GitHub), 그리고 그것을 위해 손으로 엮는 대신 성숙한 라이브러리를 원했습니다.

### 결정

- **Better Auth.** Hono에 붙고, 이미 쓰는 drizzle(PostgreSQL) 어댑터가 있으며, 비밀번호 해시 · 시도 제한 · DB 세션 · 일반 OAuth를 갖췄습니다.
  Auth.js는 비밀번호 로그인에 JWT 세션만 주고 해시 · 시도 제한 · 사용자 관리를 직접 만들어야 했고, Lucia는 지원이 끝났습니다.
  대시보드가 쓰는 엔드포인트만 열고 나머지(관리자 · 가입 · 프로필 변경)는 닫습니다. 사용자 관리는 봇 자신의 `/api/users`가 맡습니다.
- **로그인 방법은 설정 파일**(`data/auth-settings.json`)로 켜고 끄고, 비밀은 환경 변수에만 둡니다. 환경이 없는 방법은 켤 수 없고, 마지막
  하나는 끌 수 없습니다. 파일이 손상됐거나 전부 꺼져 있으면 무시하고 설정된 방법을 모두 켭니다 — 잠겼을 때 편집기로 돌아오는 길
  ([024](./024_v0.8.0_database.md)의 기준)이 로그인에서 가장 필요하기 때문입니다.
- **사용자는 한 표입니다.** GitHub ↔ 디스코드 계정 연결이 대시보드 사용자가 됩니다. 로그인 수단이 없는 사용자도 있습니다(멘션만 되는 사람).
  옛 표는 옮긴 뒤 바로 지웁니다.
- **같은 사람은 식별자로 잇습니다.** Discord 로그인은 디스코드 ID로, GitHub 로그인과 OIDC 사용자 이름은 GitHub 로그인으로 기존 사용자를 찾습니다.
  제공자의 이메일로는 잇지 않습니다: 모든 사용자의 주소는 보내지도 보이지도 않는 자리표시이고, 로그인할 때 제공자의 주소를 그 사람의
  주소로 바꿔 넣습니다. 잇지 못하면 관리자가 사용자 화면에서 핸들을 입력합니다. 본인이 입력하게 하지 않습니다 — 남의 디스코드 ID를
  주장하면 그 사람의 결산과 재생목록이 보이기 때문입니다.
- **처음 오는 사람.** OIDC는 제공자가 들여보낸 사람 모두, Discord는 봇이 있는 서버의 멤버만, GitHub는 이미 사용자에 등록된 로그인만.
- **관리자는 역할이 아니라 그룹입니다.** 사람의 그룹은 OIDC 제공자가 준 그룹(로그인마다 갱신)과 대시보드에서 준 그룹을 합친 것이고,
  `DASHBOARD_ADMIN_GROUPS`와 겹치면 관리자입니다. 팀이 이미 GitHub 팀 → Dex 그룹으로 관리자를 주고 있어서, 규칙 하나로 모든 로그인 방법에 맞습니다.
  제공자가 준 그룹은 제공자에서만 바꿉니다. 관리자는 삭제할 수 없고, 자기 관리자 권한은 뺄 수 없습니다.
- **첫 관리자는 환경 변수**(`DASHBOARD_BOOTSTRAP_*`)로 한 번 만들고 다시 덮어쓰지 않습니다. 개발용 고정 계정은 development에서만 만들고,
  프로덕션은 그런 계정이 있으면 시작하지 않습니다.
- **비밀번호**는 8자 이상, 대문자 · 소문자 · 숫자 · 기호 중 두 종류 이상입니다.

### 결과

- 업그레이드하면 모두 다시 로그인하고, OIDC redirect URI가 `/api/auth/callback/oidc`로 바뀝니다. 옛 계정 연결 표가 없어지므로 이전
  이미지로 되돌리려면 데이터베이스 백업이 필요합니다.
- Better Auth는 일반 OAuth 제공자의 discovery를 인스턴스를 만들 때 한 번만 합니다. 봇이 먼저 discovery를 해서, 제공자에 닿지 않으면
  지금처럼 `502`로 답하고 재시작 없이 다음 로그인에서 다시 시도합니다.
- Discord · GitHub 실제 로그인은 모의 제공자로만 검증했습니다.

## Context

The dashboard sent everyone straight to the OIDC provider. The flow was wired by hand on `openid-client`, and the session
was a signed cookie carrying the groups. An installation without a provider had no way in, and development used an
identity set in the environment instead of signing in. The team wanted a sign-in page, several sign-in methods that can
be switched on and off (password, OIDC, Discord, GitHub), and a mature library for them rather than more hand wiring.

## Decision

- **Better Auth.** It mounts on Hono, has an adapter for the drizzle (PostgreSQL) setup already in use, and brings
  password hashing, rate limits, database sessions and generic OAuth. Auth.js gives password sign-in JWT sessions only and
  leaves hashing, rate limits and user management to the app; Lucia is no longer maintained. Only the endpoints the
  dashboard uses are reachable — the admin, sign-up and profile endpoints are closed, and users are managed through the
  bot's own `/api/users`.
- **Methods are switched in a settings file** (`data/auth-settings.json`); secrets stay in the environment. A method
  without its environment cannot be switched on, and the last one cannot be switched off. A damaged or all-off file is
  ignored and every configured method starts on — the way back through an editor ([024](./024_v0.8.0_database.md)'s line)
  matters most for signing in.
- **Users are one table.** The GitHub ↔ Discord account links become the dashboard's users; a user may have no way to
  sign in (someone who is only mentioned). The old table is dropped once moved.
- **The same person is linked by identifier.** A Discord sign-in finds the existing user by Discord id, a GitHub sign-in
  and an OIDC user name by GitHub login. A provider's e-mail never links anyone: every user's address is a placeholder
  that is neither sent nor shown, and a sign-in replaces the provider's address with that person's. When nothing links,
  an admin enters the handle on the users page — not the person, since claiming someone's Discord id would show their
  recap and playlists.
- **Who may come in the first time.** Through OIDC anyone the provider lets through; through Discord members of the bot's
  server only; through GitHub only a login a user already has.
- **Admin is a group, not a role.** A person's groups are those the OIDC provider gives (refreshed at each sign-in) plus
  those given on the dashboard; overlapping `DASHBOARD_ADMIN_GROUPS` makes them admin. The team already grants admin
  through a GitHub team passed on by Dex as a group, so one rule covers every way of signing in. A provider's group is
  changed at the provider only. An admin cannot be deleted, and nobody takes their own admin away.
- **The first admin comes from the environment** (`DASHBOARD_BOOTSTRAP_*`), once, and is never overwritten. The fixed
  development accounts exist only in development; production refuses to start with one.
- **Passwords** have at least 8 characters and at least two of upper-case letters, lower-case letters, digits and symbols.

## Consequences

- Upgrading signs everyone out, and the OIDC redirect URI becomes `/api/auth/callback/oidc`. The old account links table
  is gone, so going back to an older image needs a database backup.
- Better Auth discovers a generic OAuth provider once, when its instance is built. The bot discovers first, so an
  unreachable provider is still a `502` and the next sign-in tries again without a restart.
- Discord and GitHub sign-in were verified against simulated providers only.
