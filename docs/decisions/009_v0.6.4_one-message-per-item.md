# 009 — One message per pull request or issue, kept current

<details>
<summary><b>한국어 — PR·Issue마다 메시지 하나, 항상 최신으로</b></summary>

- **버전:** v0.6.4
- **상태:** 채택

### 맥락

이벤트마다 새 메시지를 올리니 바쁜 채널이 넘쳤습니다. 리뷰어와 담당자가 몇 명인 PR 하나가 거의 같은 글을 줄줄이 만들었고, 사람이
추가되거나 빠지면 처음 메시지는 낡았습니다.

### 결정

PR이나 Issue를 **알린 메시지**를 추적하고, 기다리는 사람이 바뀌는 이후의 변화 — 담당자, 리뷰 요청, 제목 — 는 다시 게시하지
않고 **그 메시지를 수정**합니다. 값은 저장하지 않고 현재 이벤트로 다시 계산합니다. 수정이 실패하면 다시 알리지 않고 그 항목을
잊습니다. 다시 열리면 그 메시지가 추적을 넘겨받습니다.

### 결과

- 채널이 항목마다 항상 최신인 한 줄로 읽힙니다.
- Pipit이 메시지 ID를 기억해야 합니다(`github-messages.json`). 이 파일이 데이터베이스로 옮길 첫 대상입니다.
- 어떤 이벤트는 아무것도 게시하지 않습니다 — 발송 기록에 수정으로 남겨 왜 글이 없는지 설명합니다.

## Context

Every event becoming a new message flooded busy channels: a pull request with a few reviewers and assignees produced a
column of near-identical posts, and the opening message went stale as people were added or removed.

## Decision

The message that **announces** a pull request or issue is tracked, and later changes to who it waits on — assignees,
review requests, the title — **edit that message** instead of posting again. Values are recomputed from the current
event rather than stored. If an edit fails, the item is forgotten rather than re-announced. A reopen takes over the
tracking.

## Consequences

- Channels read as one entry per item that is always current.
- Pipit has to remember message IDs (`github-messages.json`); this file is the first thing planned to move to a
  database.
- Some events now produce no post at all — the delivery log records them as edits so their absence is explained.
