# 020 — Playlists: shared or personal, fed into the queue two at a time

- **버전:** v0.7.4 (프리릴리즈)
- **상태:** 채택

### 맥락

팀은 곡 묶음을 저장하고 한 번에 재생하고 싶어 했습니다 — 서버 모두의 것과 각자의 것 둘 다, 대시보드와 디스코드 어디서나. 곡은 듣던 곡,
검색 결과, 직접 입력, 그리고 여러 곡이 담긴 링크에서 담고 싶어 했습니다. 걸리는 점이 셋 있었습니다: 대기열의 곡은 로컬 파일이라 원래
요청을 모르고, 봇은 요청을 해석하지 않으며, music worker는 한 번에 두 곡을 준비하고 봇은 곡마다 2분을 기다립니다.

### 결정

- **공용은 누구나 고치고, 개인은 주인만** 봅니다. 주인은 디스코드 사용자이고, 대시보드 사용자는 GitHub 페이지의 계정 연결(로그인 =
  GitHub)로 디스코드 사용자에 이어집니다. 연결이 없으면 개인 재생목록은 디스코드에서만.
- 작업이 ready가 될 때 **파일마다 요청 값을 기억**해 두고, 담을 때 그 값을 재생목록에 저장합니다. 화면과 답에는 제목만 — 검색 결과처럼
  worker의 값은 서버 밖으로 나가지 않습니다(직접 친 문자열만 그대로 보여 줌).
- **재생은 피더가 두 곡씩**: 준비 중이거나 대기열에서 아직 시작하지 않은 곡이 두 개 미만일 때만 다음 곡을 요청하고, 준비가 먼저 끝난 곡도
  재생목록 순서대로 넣습니다. 30곡을 한꺼번에 요청하면 뒤쪽이 시간 초과로 실패하기 때문입니다.
- **가져오기는 일반 기능으로**: 계약의 선택 항목 `POST /v1/expand`는 "요청 하나 → 곡 여러 개"입니다. 봇은 그 요청이 무엇인지 판단하지
  않고, 풀 것이 없으면 worker가 빈 목록을 줍니다. 어떤 worker는 목록 링크를, 어떤 worker는 폴더나 재생목록 파일을 풀 수 있습니다.
- worker는 health 응답의 선택 항목 `capabilities`로 검색·가져오기 지원을 알리고, 봇은 그 입구만 보여 줍니다.

### 결과

- 대시보드 탭, `/playlist`, 리모컨 버튼, 검색 결과에서 같은 재생목록을 다룹니다.
- 재생목록 파일에는 worker의 요청 값이 남습니다 — `data/`는 원래 운영 데이터입니다.
- 봇이 재시작하기 전에 재생된 곡은 요청 값을 몰라 담을 수 없습니다.

## Context

The team wanted to save groups of tracks and play them in one go — some for the whole server, some for each person,
from the dashboard and from Discord alike — and to fill them from what was playing, from search results, from typed
text, and from a link holding many tracks. Three things stood in the way: a queued track is a local file whose request
is no longer known; the bot never reads a request; and the music worker prepares two tracks at a time while the bot
waits two minutes for each.

## Decision

- **Shared playlists are anyone's to edit; personal ones only their owner's.** The owner is a Discord user; a dashboard
  user is linked to one through the GitHub page's account links (the dashboard signs in with GitHub). Without a link,
  personal playlists are Discord-only.
- **Each prepared file remembers its request** when its job is ready, and saving stores that request in the playlist.
  Pages and answers show titles only — as with search results, the worker's values never leave the server (typed text
  is shown as typed).
- **Playing is fed two at a time**: the next track is asked for only while fewer than two are being prepared or waiting
  unstarted in the queue, and tracks enter the queue in playlist order even when a later one is ready first. Thirty
  tracks asked for at once would have the last ones time out.
- **Importing is a general feature**: the contract's optional `POST /v1/expand` is "one request → several tracks". The
  bot does not decide what the request is; with nothing to expand the worker answers an empty list. One worker may
  expand list links, another a folder or a playlist file.
- A worker states its optional features in the health answer's `capabilities`, and the bot shows only those controls.

## Consequences

- The same playlists are reachable from the dashboard tab, `/playlist`, the remote's button and search results.
- Playlist files hold the worker's request values — `data/` is operational data already.
- A track played before a restart cannot be saved: its request is no longer known.
